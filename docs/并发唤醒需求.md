## 一、目标与非目标

### 1.1 目标

1. **消灭空等待**：收件方会话一结束，后续信件立即可派发——忙碌判定从"固定 30 分钟时间窗"改为"会话生命周期信号"（进程级），完成即放行。〔r2·P1-5 限定〕本目标仅覆盖**邮局派发的无头会话**；PULL agent（workbuddy/zcode）与人工/桌面会话无 wrapper、不写闩锁，仍走 mtime 兜底（见 FR-2），其空等待属 §1.2 非目标，owner 不得按"全局消灭"验收本条。
2. **同一收件方多线开工**：多个发信方同时给同一个 agent 寄信时，在并发槽配额内**同时拉起多个无头会话**并行处理，互不阻塞；超出配额才排队。
3. **风暴防护不回退**：dead_after_dispatches（per-letter 重投上限）原样保留；新增全局在飞上限兜底，杜绝 2026-10-29 重投风暴类事故复发（项目记录第十三章）。
4. **PULL 语义零改动**：wake=TODO 的 agent（workbuddy、zcode）收发行为完全不变。

### 1.2 非目标（本期不做）

- 桌面人工会话的占用探测（owner 正在桌面窗口和 agent 对话时是否免打扰）——无头派发链只管自己拉起的会话；桌面场景留待后续（§九-2）。
- 跨机联邦下的并发协调——多机部分以《多机互联需求.md》为准，本文机制仅作用于本机邮局。
- 信件级优先级/抢占——排队仍按 FIFO，不做插队。

## 二、现状与病灶（代码级）

### 2.1 现行忙碌判定链〔r2·P1-1 修正：两个函数调用点 + 一份内联复制〕

| 层 | 位置 | 行为 | 依据 |
|---|---|---|---|
| 判定本体 | `scripts\core\common.ps1:448` `Test-AgentBusy` | 收件方 processing/、notes/ 任一文件 mtime 在 **30 分钟内** → 判忙。**Mtime-only，无会话结束事件** | 函数注释自述："Fresh recipient activity … means the agent is mid-session. **Mtime-only**" |
| route 派发前 | `scripts\core\route.ps1:145` | 判忙 → 不认领不敲门，journal 记 `recipient busy - wake deferred` | 函数注释自述设计假设："single-session CLIs reject a second one anyway" |
| sweep 内联预检 | `scripts\core\watch.ps1:310` | route 阶段对忙的收件人连子进程都不 spawn | v2.2 性能整改（项目记录第十五章） |
| 交寄侧同款 | `scripts\send.ps1:387-401` | **内联复制**的 mtime 判定（只看 processing 下 `.progress`/`.md`，**不看 notes，也不调 Test-AgentBusy**）→ 判忙 → 状态 DELIVERED＋提示 QUEUED-BUSY，副本留收件箱等拾取 | 铁律 2 的状态 token 语义 |

〔r2·P1-1〕`Test-AgentBusy` 实际只有 **2 个**函数调用点（route / watch）；send.ps1 是第三份**复制粘贴的内联逻辑**。只改函数 → 第三份原地残留 → 语义分叉。**收编内联为调函数**列为 FR-2 的实施项。另注：watch 那处对 PULL agent 是**死路径**（`$recipientPull` 先 continue，永远到不了 busy 判定），其升级不构成 PULL 收益。

### 2.2 病灶一：时间窗没有"结束"边界（owner 问题 1）

忙碌信号 = "30 分钟内有文件写入"。会话**提前完成**时，mtime 停在完成时刻，窗口照样走满——最坏白等 30 分钟。根因：系统里**不存在会话结束信号**，mtime 只是"单会话时代"的代理指标。journal 实例：2026-11-07 00:49/00:55/01:19 三次 `recipient busy - wake deferred`、02:02:50 m9w4 被挡至 02:17:22。

### 2.3 病灶二：两层串行锁封死并行（owner 问题 2）〔r2·P0-3 重定性〕

1. **逻辑层**：Test-AgentBusy 判忙即跳过——同一收件方同时只处理一封。
2. **物理层**：`scripts\adapters\hermes-wake.ps1:160-170`——"a live hermes session holds an exclusive handle on headless.log, so **the wake aborted: headless.log locked by a live session**"。

〔r2·P0-3〕**本条第二点是代码注释 + guard 逻辑推断，不是实测**：2026-11-08 复查全部 `logs\`，`wake aborted: headless.log locked` **一次都没出现过**。物理串行的真实瓶颈可能在 hermes 自己的单实例锁而非 headless.log。因此 S0（§七）第一件事是**主动复现 exit 4**；若不能复现，D3（日志拆分）就是白改——先证伪病灶二，再动刀。

### 2.4 已经并行安全的部分（本改造的地基，无需新做）

| 机制 | 位置 | 为什么天然支持并行 |
|---|---|---|
| 认领互斥 | move 即锁（inbox→processing） | per-letter 文件级，恒有一个赢家 |
| 心跳与判滞 | `<id>.md.progress` 随信 sidecar | 每封信独立计时，并行互不污染 |
| 重投计数 | 随信 sidecar 的 DISPATCHED 行数 | per-letter，与并发度无关 |
| 会话转录 | `logs\hermes\stream-<session>.jsonl` | **每会话一份**，镜像层已并行安全 |
| dashboard | v2.2 已从 route/send/claim 子进程删除 Update-Dashboard | 并行子进程无看板写竞态 |
| 回信交寄 | send.ps1 原子改名 | 并行回信安全 |

## 五、功能需求（FR，均含验收判据）

### FR-1 会话闩锁〔r2·P0-1〕

wake 适配器（含 hermes-wake.ps1 及后续各 agent 同类适配器）拉起无头会话**之前**原子创建 `logs\sessions\<agent>\<session-id>.lock`，会话进程退出后 finally 删除。

**判据**：
① 派发期间锁文件存在且内容含活 pid；
② 〔r2〕进程**正常退出**后 2 秒内锁消失（finally 覆盖）；**Ctrl-Break / 强杀下 finally 不可靠**——此类孤儿锁由 cleanup 兜底回收，判据放宽为"下一轮 sweep（≤120s）内消失"；
③ wrapper 异常路径（Ctrl-Break、子进程崩溃）最终不残留**有效**闩锁（cleanup 回收路径覆盖）；
④ 同一时刻同一 agent 最多 N 把**有效**锁（N=该 agent 槽位）——per-session 目录结构直接可数。

### FR-2 忙碌判定重定义〔r2·P1-1：含收编内联〕

Test-AgentBusy 语义改为"该 agent 有效闩锁数 ≥ 其并发槽"；`route.ps1:145`、`watch.ps1:310` 两处函数调用点同步升级，**`send.ps1:387-401` 的内联 mtime 逻辑收编为调 Test-AgentBusy（实施项，不得原地残留）**。

**mtime 兜底**（防 wrapper 老版本 / 手工调用绕过闩锁）：仅当无任何闩锁且 mtime 仍在窗内 → 判忙。**兜底窗 = 30 分钟（沿用现值，不另设参数）**〔r2：写死参数，判据可测〕。

**判据**：
① 活闩锁存在 → 判忙，与 mtime 无关；
② 锁已删 → 立即不忙（mtime 再新鲜也放行）；
③ 无锁且 mtime 在 30 分钟窗内 → 判忙（兜底路径生效）。

### FR-3 并发派发〔r2·P0-2：判据可测化〕

route 派发前查在飞数：`< 槽位` 且 `< 全局上限` → 照常认领＋拉起（每封信独立 sidecar/计数）；`≥ 槽位` → 行为与现行"忙"完全一致（不认领、journal 记 busy、QUEUED-BUSY 语义）。

**判据**：
① 〔r2〕**dispatch.log 增 `start=` 字段**（评审方案①，不依赖 FR-4 的日志拆分）：并发两会话的两条 STATUS ok 记录按 `start=`/完成时刻判**时段重叠**；
② 两封信各自 DELIVERED 且各自收到回信；
③ 第 3 封在两把锁存续期间被 defer，journal 可查；
④ 与 FR-4④ 联动：CLI 单实例拒绝**不得**计入 attempts（见 FR-4）。

### FR-4 适配器日志去单点〔r2·P2-1：补判据④〕

headless.log（wake 开始/结束行）拆为每会话一份；mirror 转录（stream-\<session\>.jsonl）不变。日志轮转与清理逻辑同步覆盖新命名。

**判据**：
① 并发两会话各写各的日志，无 `wake aborted: headless.log locked`；
② cleanup 对超过保留期的会话日志正常回收；
③ 现行 headless.log 兼容读取（历史记录不丢，仅不再追加）；
④ 〔r2·P2-1〕**CLI 单实例拒绝可识别且不计 attempts**：拆日志后 headless.log 永不冲突，现存的 exit 4"诚实失败"通道消失，单实例拒绝会退化成 exit 1 failed 照旧消耗 dead_after_dispatches（3 次即误报 RETURNED）。必须把"单实例拒绝 ≠ 派发失败"归类（exit 码识别或 wrapper 显式上报），attempts 只在真派发后累计。

### FR-5 结束即重扫〔r2：哨兵形态定案〕

wrapper finally 删锁后在 `logs\sessions\<agent>.wake-done` 落哨兵 → watch FSW → sweep route 阶段复跑。**哨兵不落收件方 inbox**（避免 route 认领撞"无 id 信封"、避免污染信件区）；watch 对该路径单独挂 FSW 或直接复用下一轮 sweep。

**判据**：
① 会话退出到下一封信 DISPATCH 的间隔 p95 ≤ 10 秒（watch 在跑时）；
② watch 未运行时退化为等下一轮 sweep/交寄侧触发，信不丢（≤120s）。

### FR-6 pid 复用防护

闩锁有效性 = pid 存活 **且** 进程启动时间与锁内记录一致（Windows pid 会复用）。

**判据**：
① 伪造一把 pid 为现活进程、启动时间不符的锁 → 判定无效，cleanup 清除；
② 真会话锁全程有效。

### FR-7 兼容回归〔r2：补 QUEUED-BUSY 回归〕

PULL agent（wake=TODO）全链路不变；dead_after_dispatches 行为不变。

**判据**：
① test-deadletter.ps1 CB/CC/CD 用例全绿；
② workbuddy 收信仍 `no wake command (PULL mode); message … waits in inbox for mail-check pickup`；
③ 〔r2〕send.ps1 内联忙判定收编后，**QUEUED-BUSY 分支（send.ps1:391-400）回归验证**——重构不得丢掉"route 失败后区分 busy / dead"这条善后。

## 九、风险与开放问题〔r2·P1-4 + P2-1：补两条〕

1. **hermes CLI 是否真支持双开**——S0 前置实测定论；若单实例，问题 2 对 hermes 无解（保持槽 1），但问题 1 的收益（闩锁判忙）对所有 agent 都成立。
2. **桌面会话占用**——workbuddy 的教训（桌面端占 46232 端口致无头 EADDRINUSE）说明"桌面在跑"本身就是无头的潜在冲突源。本期不探测桌面进程；若 S4 灰度出现该类失败，退路是给受影响 agent 保持槽 1。
3. **哨兵触发风暴**——FR-5 的哨兵走现有 FSW 2 秒去抖，理论无放大；S4 观察 SawEvent 频率确认。
4. **与 v3 的关系**〔r2：真实风险点改写〕——pid 闩锁与 v3 的 per-topic status.json 正交（一个管进程生命周期、一个管话题状态）。真正的交互风险在 **chain 副本**：`route.ps1` 的 `$isChain` 分支下副本不认领、原地响铃、不消耗 attempts——槽满时 chain 副本会被反复 defer 而**永远不产生 DISPATCHED 行** → 不会 RETURNED，也不会推进 v3 的 topic 状态，在 status.json 里表现为"pending 且无人处理"。v3 一期把 defer 原因写进 status.json（如 `deferred: in-flight 2/2`），否则 owner 在后台看不到卡在哪。
5. **mirror 并发写**——每会话独立 out 文件已天然安全；仅会话 id 碰撞（同秒同 id）需在 S1 用时间戳＋pid 后缀兜底。〔r2〕另：mirror 进程自身的锁与双会话文件归属在 S0-③ 专门实测。
6. 〔r2·P1-4〕**prepare lock 互踩**——比端口 EADDRINUSE 更隐蔽：端口冲突会明确失败，锁互踩可能表现为"两个会话都起来了但配置半新半旧"。S0-② 专门测时序；若确认互踩，S1 给 prepare.lock 的探测-删除加原子重试或进程内串行化。
7. 〔r2·P2-1〕**exit 4 通道消失 → attempts 被耗光**——并发化后最可能的新事故：单实例 CLI 拒绝一次就记一条 DISPATCHED，3 次 RETURNED 误报。必须先有"拒绝 ≠ 失败"的归类（FR-4④），**再开并发**。
