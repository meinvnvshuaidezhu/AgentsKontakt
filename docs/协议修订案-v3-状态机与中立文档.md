## 0. 摘要

v3 把信件生命周期从「多封独立信件的链 + 碎片化状态信号」重构为：

1. **话题状态机**：每话题一个 `status.json`，四态 `待领取 → 正在处理 → 已答复 → 已归档`；「待领取」的变更只有收件方认领时才发生；登记收件方的答复永远有效（与当前状态无关，防判滞降级竞态）；
2. **中立文档**：邮差在自辖区持有话题**唯一真身**（对话 + 思考链引用按轮次追加，原子写入 + id 去重），双方邮箱里只是**按话题覆盖式**投递副本，答复/归档后副本清除；
3. **元数据判活总纲**：邮差读本机文件元数据（大小/mtime/存在性），不读信件正文与思考录内容；判活 = 状态心跳 **或** 思考录元数据变化；
4. **归档看状态、大小管分割**：归档闸 = `已答复` 后发起方确认（`nudge_after_days=7` 双方催办（发起方、收件方；owner 抄送未实装）、`auto_archive_after_days=14` 自动归档，均自 answered 起算）；单文件超 64 KB 滚动分割、旧件只读、链式引用、全链投递；
5. **归档索引 JSONL**：`archive\index.jsonl` 追加式索引，一次归档、提问者与回答者各可查，零新依赖；
6. **入箱校验**：无 v3 痕迹登记的 inbox 文件拒列——绕过投递接口的**误用型**信件进不了正式视野（legacy 在途豁免，见 §2.6）。

## 1. 新旧方案对比

| 维度 | 现行（v2.x） | v3 修订案 |
|---|---|---|
| 状态载体 | 碎片：`.status`（只记投递）、`.progress`（心跳日志）、`state: open`（形同虚设） | 每话题一个 `status.json` 状态机（四态 + 心跳时间戳 + 链清单） |
| 状态可见性 | 发件方不可见对方进度，只能等回执/STALLED | 双方随时读状态文件；每次状态迁移邮差打铃通知对方 |
| 状态写权限 | 邮差写 .status、agent 写 .progress，互不知晓 | 收件方独占常态迁移；邮差写仅限例外清单（判滞降级/超时自动归档/转投执行）；发起方追问、归档确认、转投一律经 send.ps1 表达（status.json 对发起方只读）；登记收件方答复与状态无关永远有效 |
| 回答后痕迹 | 原请求信留收件方 inbox 占待处理视图（缺口 1） | 双方邮箱零正文残留：答复进中立文档，副本答后即清 |
| inbox 副本策略 | 每轮投递新增一份文件，多轮累积 | **按话题覆盖式**落 `<topic>.chain.md`，每话题恒一份最新全链视图 |
| 答复形态 | 独立新信；话题 = 多封信的链 | 答复追加进中立文档（带日期 + 思考链路径）；话题 = 一份持续增长的会话文档 |
| 真相持有 | 双方各持副本，归档时全信箱拼合 | 邮差单源持有，双方只是投递视图；**入箱校验挡影子信件** |
| 上下文传递 | 收件方只收单封信，回溯靠 archive-query | 每次投递带全链副本（含此前全部轮次），收件方零查询 |
| 一致性 | 正本/副本独立，归档靠内容 dedupe | 单源天然一致 + chain 清单对账（integrity） |
| 归档触发 | 发起方手动 close（忘 close 即滞留——实战案例） | 发起方确认 + `nudge_after_days=7` 双方催办 / `auto_archive_after_days=14` 自动归档（均自 answered 起算，配置项，默认开——见 §2.2） |
| 归档索引 | markdown 双层表（index.md / _index.md） | `archive\index.jsonl` 追加式索引，一次归档双记录可查，零依赖 |
| 归档只读 | archive\ + lockdown ✓ | 不变 ✓；归档对象只有中立文档链，无拼合步骤 |
| 心跳/判活 | .progress mtime + notes mtime（伴生） | `last_heartbeat` 字段 或 notes 元数据变化；总纲：邮差读元数据不读私有内容 |
| 停滞处置 | STALLED 广播 + requeue + 退回，无推进力（缺口 3） | 保留全部机制对象改状态机；5 分钟中性提醒 + 状态迁移通知 + pending 永滞终态处置 |
| 大文件 | 无机制 | 64 KB 滚动分割、旧件只读链式引用、全链投递；链总长 256 KB 三方提醒（不强制） |
| 记账 | journal 动作流水 | 保留；分工：中立文档 = 内容账本，journal = 动作账本 |
| 写入防御 | 无（空壳可覆盖正本——2026-11-06 实战事故） | sent 落位防覆盖、take 时 id 查重、退信附字节数、取件预检 + 滞留强制退信 |

### 消灭的缺口

- **缺口 1**（已答信占待处理视图）：状态机「已答复」+ 副本即清 + 按话题覆盖 → 根治。
- **缺口 2**（绕过 send.ps1）：正文唯一真身在邮差辖区 + **入箱校验**——**根治误用型绕过**（写入方绕过管线且未登记；**拦截能力自 sweep 移除 legacy 分支起完全生效**，过渡期见 §2.6 能力边界）；**不构成对恶意伪造的防护**——伪造 status.json 的写入方与本协议同级信任模型，超出范围（威胁模型按评审 E 收紧）。
- **缺口 3**（停滞无推进力）：状态迁移通知 + 5 分钟提醒 + answered 超时自动归档 + pending 永滞终态 → 根治。
- **缺口 4**（写入防御缺失，事故新增）：空壳覆盖正本、无效信重走管线 → 四条管线防御 + 取件预检 → 根治。

## 2. 核心对象定义

### 2.1 中立文档（话题文档，邮差持有）

- 位置：`post\threads\<topic>\thread-<n>.md`（`post\` 为邮差自辖区，不入 git、不属任何 agent 邮箱）
- 创建：A 首次发起话题时由邮差创建 `thread-1.md`
- front-matter：

```markdown
---
topic: t-20261106-<hash>
from: <发起方>
to: <收件方>
seq: 1            # 链序号；分割后 2、3…
inherits:         # 前件文件名（seq>1 时必填）
  - thread-1.md
created: <ISO8601>
---
```

- 正文按轮次追加，每轮一个块：

```markdown
## [2026-11-06T10:00:00+08:00] A 追加提问
<!-- kind: question   （answer / archive-note 同理；状态迁移按 kind 判定，见 §2.2） -->

<正文>

思考链：mailboxes/A/notes/t-20261106-<hash>.md
```

- **每轮块必须带 `kind: question | answer | archive-note`**（HTML 注释或行内标记）——状态迁移按 kind 判定，不靠看正文猜
- 思考链只写**路径引用**，内容仍留在思考者自己的 `notes\`（私有，邮差不读）
- 状态到达 `archived` 前最后一个活动件可写；旧件一经分割即只读
- **追加原子性**：追加与分割必须串行——**per-topic 锁定稿：锁文件 `post\threads\<topic>\.lock`（独占创建，超时 10s 让路重试，超 60s 视为僵尸锁：告警 + 记录持有者 PID 后可回收）；status.json 一律 temp+rename 写；读侧容忍半写（解析失败视为瞬时，重读一次）**；**id 去重**：追加前查 chain 末轮已有 id，防 watcher 兜底重试造成双追加（2026-11-06 事故实证此路径）
- **processing 态禁止追加**：收件方正在处理时发起方不得追加新轮（回合制铁律的机器化）；追问必须等 answered——防止 B 基于旧上下文作答后链里夹着 A 的新轮，轮次边界脏

### 2.2 状态文件（唯一真身，单源）

- 位置：`post\threads\<topic>\status.json`；一个话题一个文件，独立于收发邮箱，双方随时可读

```json
{
  "topic": "t-20261106-<hash>",
  "from": "A",
  "to": "B",
  "state": "pending",
  "last_heartbeat": "2026-11-06T10:05:00+08:00",
  "state_updated_by": "postmaster",
  "state_updated_at": "2026-11-06T10:00:00+08:00",
  "chain": ["thread-1.md"],
  "chain_bytes": 8421,
  "delivered_at": "2026-11-06T10:00:05+08:00"
}
```

- **schema 补充（复审 B1/B2 定稿）**：`copies` 对象记录投递痕迹（`{"<agent>":{"delivered_at":…,"bytes":N,"cleared_at":…}}`，配合 §2.6 三源判定）；归档时状态文件随链移入归档目录、`state` 置 `archived` 并补 `archived_at` 字段（§3 第 5 步）。

- **写权限矩阵**：状态文件由邮差在创建话题时写入初始态 `pending`；此后「待领取」的变更只有一种触发——收件方认领时自己修改，邮差与发件方对它只读。**常态迁移由收件方独占；邮差写状态仅限下方例外清单**。

| 迁移 | 谁执行 |
|---|---|
| pending → processing | 收件方（认领时） |
| processing → answered | 收件方（send.ps1 落 answered；收件方进程已死场景见转投/close） |
| answered → pending（发起方追问） | 发起方（send.ps1 代写） |
| answered → archived | 发起方确认（手动） |
| answered → archived（超时自动） | 邮差（自 answered 起算：`nudge_after_days=7` 首次催办、`auto_archive_after_days=14` 自动归档，两个独立配置项，默认开） |
| processing → pending（超时降级） | 邮差（判滞触发，sys 邮通知双方） |
| pending → pending（转投） | 邮差（发起方 `send.ps1 -Redirect -Topic <t-...> -RedirectTo <新收件方>` 触发） |

**邮差写状态的例外清单**：①判滞降级 ②answered 超时自动归档 ③转投执行——除此之外邮差不写状态；发起方对 status.json 一律只读，一切意图通过 send.ps1 管线表达（含追问、归档确认、转投）。
**archived 为终态、无出边**：追问一律开新话题（§3 第 5 步），禁止实现 reopen。
**迁移按追加块 `kind` 字段判定**（§2.1）：kind=question → pending（追问），kind=answer → answered，kind=archive-note → archived——不靠看正文猜。

- **pending 态答复竞态（评审缺口 3）**：send.ps1 接受答复的条件 = `from == status.to`，与当前 state 无关——登记收件方的答复永远有效、直接落 answered；判滞降级不剥夺答复权。
- **pending 永滞转投（写死）**：pending 超时（收件方死亡）sys 邮通知发起方二选一：close 结案，或转投。**转投 = 发起方跑 `send.ps1 -Redirect -Topic <t-...> -RedirectTo <新收件方>` 触发、邮差原子执行**：改 `status.to` → state 置 pending → `delivered_at`/`last_heartbeat` 重置 → **清原收件方 inbox/processing 该 topic 副本** → 向新收件方投全链（走取件预检）→ journal 记 `STATE redirect` → sys 邮通知新旧收件方双方。

### 2.3 与五区的衔接

| 区 | v3 角色 |
|---|---|
| `inbox\` | 收**按话题覆盖式**的中立文档链副本 `<topic>.chain.md`（每话题恒一份最新视图，不随轮次累积）；答复后发件方清自己的请求副本；归档后全部清除 |
| `outbox\` | 投稿暂存，watch 取件后清空（不变）；取件预检 + 滞留强制退信见 §2.5 |
| `sent\` | 一期仍写**正本全文**（叠加 §2.5-1 落位防覆盖）；**存根化（仅 front-matter 引用，无正文）为二期目标**——A 借存根知道自己发过什么、此刻到了哪一步，内容沿引用调取（定稿口径：§6 一期不做与 §2.3 以本括注为准） |
| `processing\` | v3 流程不强制使用（信件不再物理移动）；保留目录兼容长任务习惯（定案） |
| `notes\` | 不变；元数据（mtime/size）升格为正式判活信号源 |

### 2.4 归档索引（JSONL，零依赖——定案）

归档不仅移动物理链，还追加写**归档索引** `archive\index.jsonl`（一行一条记录，追加式）：

```json
{"topic":"t-20261106-<hash>","title":"...","initiator":"A","responder":"B","start_date":"2026-11-06","closed_time":"2026-11-06T10:00:00+08:00","thread_ref":"archive\\A\\2026\\11\\06\\t-20261106-<hash>\\","participants":[]}
```

- **一次归档，双记录可查**：提问者与回答者都能查到（`initiator=? OR responder=?` 或 participants 包含）——双方都知道话题已归档、存于何处。
- `thread_ref` 指向 lockdown 后的只读链：只能引用调取、不可编辑，不放在任何 agent 的收发邮箱中。
- **广播话题不入库**（无 responder）；`participants` 预留数组字段承载未来多方话题。
- **写入纪律（复审定稿）**：追加由邮局**单写者串行**（archive.ps1 持 index 锁，与 per-topic 锁同纪律）；archive-query **逐行容错**——崩溃中断产生的半行按行 try/catch 跳过 + 计数告警输出，一条坏行不得炸掉整个查询。
- **JSONL 回灌（复审 C1 定稿，与 sweep 脱钩）**：回灌 = **切后端前的一次性快照动作**，独立于 sweep——从 `archive\index.md` + `archive\<agent>\_index.md` + archive 目录扫描**三方并集去重**回灌；判据 = 快照时刻三方并集去重后的 topic 集合 == 回灌后 JSONL 的 topic 集合（三源数量天然不等，不得用"总数一致"当判据）；**回灌与 archive.ps1 持同一把 index 锁**（防回灌期间新归档双写乱序）；按 topic 键去重追加、可重跑幂等；**sweep 只是清 legacy 在途 + 移除 legacy 分支的独立动作，与 JSONL 无依赖**。
- 查询后端：`archive-query.ps1` 改读 JSONL（ConvertFrom-Json 过滤，千条话题前无性能差异）；物理链仍按 `archive\<发起方>\<年>\<月>\<日>\<topic>\` 布局。
- 零依赖定案理由（评审采纳）：查询负载低频；零依赖是发布优势，随包 exe 抬高 Defender 误报成本；JSONL 人类可读可 grep；将来如需 SQL 可一次性导入，反向不可。
- markdown 双层索引（index.md / _index.md）保留为**人读视图**，由归档动作从 JSONL 再生成。

### 2.5 管线写入防御（2026-11-06 事故四条，全部纳入一期）

| # | 防御 | 规则 |
|---|---|---|
| 1 | sent 落位防覆盖 | master 移入 sent\ 前检查同名已存在 → 拒绝并保旧件 + 告警 sys 邮**（抄送 owner——发起方 agent 可能已死，告警落其 inbox 无人读；与 256KB 三方提醒同口径）**（不做 .1/.2 改名，sent 语义是每 id 一正本） |
| 2 | take 时 id 查重 | 管线取件时按 id 查 sent\ 与对方 inbox，已 DELIVERED/RETURNED 的 id 按 duplicate 拒绝重走管线；v3 对应 chain 末轮 id 去重 |
| 3 | 退信附正本字节数 | bounce sys 邮带 `master_bytes: N`，截断类事故一眼可辨 |
| 4 | watcher 取件预检 | **确定性校验**：读入后**先剥离 UTF-8 BOM 再判定**（`ReadAllText(…, UTF8)` 语义，BOM 存在与否不影响结果——否则 §2.7 鼓励的带 BOM 信件会被自伤式全退）；front-matter 六字段齐全（id/topic/from/to/type/created）且 **id 匹配 `^msg-\d{8}-\d{6}-[a-z0-9]+-[a-z0-9]{4}$`（幂等键格式，防乱码 id 静默污染去重体系）、created 可被 `[datetime]::Parse` 解析（判滞窗口全依赖它）** + 闭合 `---` + 正文非空；字节阈值（<32）保留为快速前置；任一不满足不取，滞留超 10 分钟 → 强制取走退信（reason: invalid-envelope） |

### 2.6 入箱校验（评审缺口 2 收紧 + legacy 豁免 + 三源判定）

- `mail-check.ps1` / watcher 对 inbox 内**存在 v3 痕迹却无合法 status.json 登记**的 msg-*.md 文件：标记 `unofficial`（不列入待处理计数）或直接拒列——影子信件不仅不进档案，还进不了正式视野。
- **v3 痕迹判定 = 三源任一命中**（复审 B2 定稿）：① `post\threads\<topic>\status.json` 存在；② journal 中该 topic 有 `THREAD`/`STATE` 记账行；③ `sent\` 存在该 topic 的存根/正本。配合 §2.2 schema 的 `copies` 对象（`{"<agent>":{"delivered_at":…,"bytes":N,"cleared_at":…}}`）——"投递过"有持久证据，不靠 inbox 现状推断（副本答复即清后，status.json/journal/存根仍是痕迹）。
- **legacy 豁免（复审必改-1，一期上线前提）**：三源全不命中的 msg-*.md 属 legacy 在途（v2 语义，close 走 legacy 分支），**照常列入待处理**，直至 §7-5 sweep 清零后自然退出。否则一期上线瞬间存量信件集体从视野消失。
- **合法/非法判定**：正例 = inbox 副本登记信息与 `post\threads\<topic>\status.json` 的 topic/from/to 一致且状态文件存在；反例 = 该 topic 有 status.json 但 inbox 文件登记与之不匹配（from/to/topic 对不上）→ unofficial。
- **一期能力边界（书面承认，复审 R6 定稿）**：legacy 豁免期内，「无痕迹」既可能是 v2 在途信也可能是绕过管线的影子信，二者**不可区分**（豁免与校验的判据互为补集），故入箱校验对无痕迹文件不生效——**缺口 2 的拦截能力自 §7-5 sweep 移除 legacy 分支之日起才完全生效**。过渡期接受此残留风险，以「journal 有该 topic 的 v2 SEND 记录」作为弱旁证：命中则倾向 legacy，不命中仅记 `legacy-suspect` 标，**不作拒列**。

### 2.7 编码纪律分两档（评审采纳）

| 对象 | 纪律 | 原因 |
|---|---|---|
| 脚本、配置、状态文件等**程序数据文件** | 必须 UTF-8 with BOM | PS 5.1 无 BOM 按 GBK 读的锅 |
| **信件正文**（front-matter + 正文） | 解析器实测不要求 BOM（ASCII front-matter 无 BOM 照样送达）；建议仍带 BOM，门禁缺 BOM 自动补不退信 | 避免"以为要补 BOM"的时序操作反成事故源头（2026-11-06 实证） |
| `archive\index.jsonl` | **UTF-8 no-BOM**（复审增补；脚本侧 .NET 显式 UTF8 读，不依赖编码猜测） | 带 BOM 的首行会让 jq 等第三方 JSONL 工具解析失败 |
| 文件名 | 只用 ASCII（不变） | 跨工具链兼容 |

## 3. 新生命周期（五步对应原需求）

1. **A 发起**：`send.ps1 -To B` → 信封门禁 → 邮差创建中立文档 `thread-1.md`（原子写）+ `status.json`（pending）→ 链副本按话题覆盖式投 B 的 inbox + 按收件方 wake 链打铃 → A 的 `sent\` 写**正本全文**（叠加 §2.5-1 落位防覆盖；存根化为二期目标，见 §2.3）。
2. **副本同步**：投递/追加动作后，邮差把当前全链以 `<topic>.chain.md` 覆盖式复制到对方 inbox。
3. **B 认领**：改状态 processing + 刷新 `last_heartbeat`（处理期间持续刷新）→ 处理（思考录随手写，元数据即判活信号）。
4. **B 答复**：`send.ps1` 回信（条件 = `from == status.to`，与 state 无关）→ 邮差原子追加进中立文档（带日期 + 思考链路径，id 去重）→ 状态 answered → 全链副本覆盖投 A 的 inbox → **邮差清除收件方（B）该 topic 的全部文件——清理范围 = `inbox\` 与 `processing\`（B 若按 v2 习惯把副本 move 进了 processing 也在内）；清理失败（占用/权限）→ journal 记 `CLEANUP_FAILED` + sys 邮告警，不得静默**。B 零痕迹。
5. **A 收束**：A 读副本即完整对话；**追问**：answered 态下 A 追加新轮（kind=question）→ 副本重投 B，状态回 pending（重复 2–4）；**已归档话题的追问** = 开新话题 + 首轮正文带 `thread_ref` 引用旧链，不设 reopen；任务结束 → A 追加归档留言（kind=archive-note）→ 状态 archived（手动；14 天超时自动）→ **中立文档整链 + `status.json`（最终态 archived、补 `archived_at` 字段）一并移入** `archive\<发起方>\<年>\<月>\<日>\<topic>\`（lockdown 只读；status.json 归档保留是"何时 closed"的证据，且 integrity 对账要求 post\threads 下不留孤儿）→ `post\threads\<topic>\` 整目录清空 → 写 JSONL 归档记录（双记录）→ A 侧副本清除（B 侧早已清空）。**integrity 对账口径**：`post\threads\` 下每个 topic 目录必含 status.json + 至少一个 thread-*.md，chain 清单与实际文件双向对账。

## 4. 分割与归档规则

- **归档闸**：`answered → archived`——发起方确认（默认）；**自 answered 起算** `nudge_after_days=7` 首次双方催办（发起方、收件方；owner 抄送未实装）、`auto_archive_after_days=14` 邮差自动归档（与 §2.2 同一对配置项，默认开）。文件大小不触发归档。
- **分割**：活动件追加后超 **64 KB** → 新开下一序号文件（`inherits` 指向前件），前件立即只读；追加与分割串行（per-topic 锁）。
- **投递带全链**：每次投递以 `<topic>.chain.md` 覆盖式复制当前全链。
- **软提醒**：全链总量超 **256 KB** → sys 邮提醒**三方（含 owner）**「该结案了」，不强制。
- **分割事件不单独通知**：对方从副本 front-matter 的 `seq`/`inherits` 自知链已跨文件，避免实现时纠结。
- 旧件只读由邮差在分割时落锁定属性；archive lockdown 机制沿用现行。

## 5. 通知矩阵与判活

| 事件 | 通知 | 渠道 |
|---|---|---|
| 状态迁移 | 通知对方 | 对方 wake 降级链（复用现行） |
| 投递后 5 分钟仍 pending | 发件方中性提醒「尚未领取」 | 邮差 sys 邮（定案） |
| outbox 文件滞留超 10 分钟 | 强制取走退信 invalid-envelope + sys 邮告警 | 邮差（§2.5-4 兜底） |
| 在途 30 分钟无活动（`stall_minutes=30`，沿用现行） | STALLED 升级提醒 | 现行判滞机制，对象改状态机 |
| answered 超 7 天无动作 | 双方催办 | sys 邮 |
| 全链 > 256 KB | 三方（含 owner）「该结案了」 | sys 邮 |
| processing 超时（心跳与 notes 元数据均停摆） | 降级 pending + sys 邮双方 | 邮差 |
| pending 永滞（收件方死亡） | 发起方：close 或转投 | sys 邮 |

**判活**（元数据总纲）：`last_heartbeat` 新鲜 **或** `mailboxes\<收件方>\notes\<topic>.md` 的 mtime/size 近期有变化 → 视为在执行；两者均停摆超判滞窗口 → 降级/提醒。邮差只读元数据，不读两者内容。**文档配套**：mailbox skill v3 改版时重申「每个关键节点写心跳」铁律（评审 §3e——LLM 全程回合内工作不落盘的场景靠心跳纪律覆盖）。

**信封门禁（复审 R 终轮增补）**：`type: reply` 且正文含问句（问号结尾的疑问）时**不得标 `NO-REPLY`**——门禁检测到即告警拒发，防止"问了没人答"的静默停滞（2026-11-06 实证：带问句的 NO-REPLY 信可让定稿流程无限期卡住）。

## 7. 实施约束（所有者指示）

1. **E 盘仓库零数据**：`post\threads\`、`mailboxes\`、`archive\` 等运行数据只存在于安装实例；任何测试不在 E 盘跑出数据。
2. **产物 = 安装包**：实现完成后产出 dist 安装包，所有者自行安装到 D 盘正式测试。
3. **自测模式**：send/claim/archive 提供 `--selftest`——临时目录自建 root 跑发起→认领→答复→归档全链路回归，纳入一期验收判据（E 盘零数据纪律下的测试出口）。
4. 开源合规：core 零专名、文案走 i18n、脚本 ASCII、程序数据文件 UTF-8 BOM（两档纪律见 §2.7）。
5. **存量兼容**：不做一次性迁移（评审采纳）——存量在途话题按 v2 语义自然走完，`close.ps1` 旧路径保留 legacy 分支（按有无 status.json 自动分流）；存量清零后跑一次 sweep 收尾残留，再移除 legacy 分支。
